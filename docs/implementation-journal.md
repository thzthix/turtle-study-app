# Implementation Journal

이 문서는 Turtle Study App의 구현 과정에서 생긴 판단과 고민을 기록하는 일지다.

목적:

- 구현 이력만이 아니라 의사결정 맥락을 남긴다.
- 설계 변경 이유를 나중에도 추적할 수 있게 한다.
- PM 관점과 구현 관점을 함께 연결한다.

---

## 2026-05-18 - 프로젝트 가이드 문서화

### 작업 목표

- 구현 전에 제품 방향, 작업 규칙, UX 흐름을 문서로 고정한다.

### 구현 내용

- `README.md`에 프로젝트 개요와 현재 범위를 추가했다.
- `AGENTS.md`에 범위, 디자인, 코드, 브랜치, 커밋 규칙을 정리했다.
- `docs/mvp-spec.md`에 MVP 가설, 기능 범위, 성공 기준을 정리했다.
- `docs/ux-flow.md`에 화면 구성과 상태 흐름을 정리했다.

### 설계 상 고민

- 코드부터 시작하면 빠르게 만들 수 있지만, 감성형 제품은 기준 없는 상태에서 구현을 시작하면 쉽게 산만해질 수 있다고 판단했다.
- 특히 이 앱은 생산성 앱이면서 동시에 정서적 캐릭터 경험이 중요하므로, 기능보다 먼저 제품 중심축을 고정할 필요가 있었다.

### 구현 중 고민

- 문서를 너무 무겁게 만들면 초반 속도가 느려질 수 있었다.
- 반대로 문서가 너무 얇으면 이후 브랜치들이 제각각 방향으로 갈 위험이 있었다.

### 트러블슈팅

- 원격 저장소가 비어 있어서 첫 작업 브랜치로는 정상적인 PR 생성이 되지 않았다.
- 첫 문서 커밋을 기준으로 `main` 브랜치를 부트스트랩해 이후 브랜치 전략이 정상 동작하도록 정리했다.

### 고려한 대안

- 대안 1: 문서 없이 바로 UI 구현 시작
- 대안 2: README만 간단히 쓰고 나머지는 구현하면서 보강
- 대안 3: 제품 명세, UX 흐름, 작업 규칙을 먼저 모두 작성

### 최종 선택과 이유

- 대안 3을 선택했다.
- 이유는 이 프로젝트가 감성, 상호작용, 생산성의 균형이 중요해서 초반 기준 문서가 이후 속도를 오히려 높여줄 가능성이 크다고 봤기 때문이다.

### 남은 TODO 또는 리스크

- 다음 브랜치부터는 실제 구현과 함께 일기 기록도 계속 누적해야 한다.
- 구현이 시작되면 문서와 실제 UI가 어긋나지 않는지 수시로 점검해야 한다.

## 2026-05-18 - 구현 일기 체계 추가

### 작업 목표

- 이후 모든 기능 구현에 적용할 수 있는 구현 일기 규칙과 템플릿을 레포에 추가한다.

### 구현 내용

- `AGENTS.md`에 구현 일기 작성 규칙을 추가했다.
- `README.md`에 구현 일기 문서를 연결했다.
- `docs/implementation-journal.md` 파일을 만들고 초기 기록을 남겼다.
- `docs/implementation-journal-template.md` 파일을 만들어 이후 브랜치 작업에 재사용할 수 있게 했다.

### 설계 상 고민

- 구현 일기가 단순 회고처럼 흐르면 실제 의사결정에 도움이 적을 수 있었다.
- 그래서 감상보다 `왜 이 선택을 했는지`가 드러나는 구조가 필요했다.

### 구현 중 고민

- 일기 형식을 너무 빡빡하게 만들면 개발 흐름을 방해할 수 있었다.
- 반대로 형식이 느슨하면 중요한 맥락이 빠질 위험이 있었다.

### 트러블슈팅

- 별도 문제는 없었지만, 구현 일기 규칙이 실제로 강제되지 않으면 금방 형식화될 수 있다고 판단했다.
- 이를 막기 위해 `AGENTS.md`의 작업 규칙과 PR 흐름 안에 일기 기록 요구를 명시했다.

### 고려한 대안

- 대안 1: 매 작업 후 채팅으로만 설명 남기기
- 대안 2: README 하단에 간단한 로그만 누적하기
- 대안 3: 전용 구현 일기 문서와 템플릿을 별도로 운영하기

### 최종 선택과 이유

- 대안 3을 선택했다.
- 이유는 기능 단위로 설계 판단, 구현 고민, 트러블슈팅을 구조적으로 누적해야 나중에 회고와 유지보수에 모두 도움이 되기 때문이다.

### 남은 TODO 또는 리스크

- 이후 실제 구현 브랜치에서도 이 문서가 빠지지 않도록 계속 유지해야 한다.
- 일기 항목이 길어지더라도 핵심 판단이 흐려지지 않게 관리할 필요가 있다.

## 2026-05-18 - 집중 세션 UI MVP 구현

### 작업 목표

- 웹에서 바로 동작하는 첫 집중 세션 경험을 만든다.
- 거북이 동행 콘셉트가 한 화면 안에서 이해되도록 구성한다.

### 구현 내용

- React + TypeScript + Vite 기반의 웹 앱 구조를 추가했다.
- `useFocusSession` 훅으로 세션 시간, 진행률, 돌봄 시점, 완료 상태를 관리하도록 분리했다.
- 집중 시간 선택, 시작, 초기화가 가능한 `SessionPanel`을 구현했다.
- SVG 기반 거북이 일러스트와 산책 경로 애니메이션을 가진 `TurtleScene`을 구현했다.
- 물 주기/당근 주기 돌봄 인터랙션을 `CarePrompt`로 분리했다.
- 완료 보상, 여정 요약, 친구 거북이 보드를 각각 별도 컴포넌트로 나눴다.
- 따뜻한 크림/세이지/살구 계열 배경과 느린 모션 중심의 스타일을 추가했다.
- `.gitignore`와 TypeScript 빌드 설정을 정리해 불필요한 생성물이 커밋 대상에 섞이지 않게 했다.

### 설계 상 고민

- 처음부터 서버나 저장 기능을 넣으면 제품의 핵심 감정선보다 구조가 앞서갈 수 있다고 판단했다.
- 그래서 이번 브랜치는 `한 번의 집중 세션이 기분 좋게 끝나는가`에만 집중했다.
- 또한 거북이 일러스트를 이미지 파일로 넣는 대신 SVG로 작성해 이후 감정 표현을 코드에서 바로 조정할 수 있게 했다.

### 구현 중 고민

- 돌봄 상호작용이 자주 뜨면 집중을 깨고, 너무 드물면 존재감이 약해질 수 있었다.
- 그래서 체크포인트를 세션 중 2회로 제한하고, 응답 후에는 다시 조용한 걷기 상태로 복귀하게 설계했다.
- 소셜 보드는 실제 기능 없이도 분위기를 줄 수 있도록, 초기에는 정적 카드 UI로 제한했다.

### 트러블슈팅

- 의존성 설치는 기본 샌드박스 상태에서 진행이 멈춰서, 권한을 올려 설치를 다시 수행했다.
- 설치 후 `npm run build`를 바로 실행해 타입과 번들 단계가 모두 통과하는지 확인했다.
- 초기 `tsc -b` 구성은 불필요한 산출 파일을 만들 수 있어서 `tsc --noEmit` 기준으로 단순화했다.

### 고려한 대안

- 대안 1: Next.js로 바로 시작하기
- 대안 2: 정적 HTML/CSS 프로토타입으로만 먼저 만들기
- 대안 3: React + TypeScript + Vite로 가볍게 시작하기

### 최종 선택과 이유

- 대안 3을 선택했다.
- 이유는 UI 상호작용과 상태 전환이 많은 제품이라 React가 적합하고, Vite가 MVP 속도와 구조 단순성 사이 균형이 가장 좋았기 때문이다.

### 남은 TODO 또는 리스크

- 실제 브라우저에서 애니메이션의 체감이 과하지 않은지 추가 확인이 필요하다.
- 세션 일시정지, 이탈 감지, 기록 저장 같은 기능은 아직 범위 밖이다.
- 디자인 완성도를 높이려면 거북이 표정 변화와 배경 디테일을 한 단계 더 다듬을 수 있다.
